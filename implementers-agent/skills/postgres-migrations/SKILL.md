# PostgreSQL migrations

**The repo's own migration tool and conventions always win.** These defaults assume Alembic.

## Writing the migration
1. One migration per task. Generate the revision with the repo's usual command (for example `alembic revision -m "<short description>"`), then write `upgrade()` and `downgrade()` by hand. Review any autogenerated content line by line.
2. Match the DDL in the contract exactly: names, types, nullability, defaults, constraints and indexes.
3. Use the naming conventions the repo already uses for constraints and indexes.
4. Update the SQLAlchemy model only if the model file is in your `files_in_scope`. Otherwise the Python task owns it.

## Safety rules for existing tables
| Change | Safe approach |
|---|---|
| Add a column | Nullable, or with a server default. Never add `NOT NULL` without a default to a table that has rows |
| Make a column NOT NULL | Expand: add it nullable -> backfill -> set NOT NULL in a later migration or step |
| Rename or drop a column or table | **Do not** in iteration 1 unless the plan explicitly says so: it breaks running code. Expand / contract across releases |
| Add an index on a large table | Use `postgresql_concurrently=True` inside an autocommit block, if the repo does this already |
| Backfill data | Batched update, not one huge statement. Keep it idempotent |
| Change a column type | Treat as high risk. Return BLOCKED unless the plan gives the exact approach |

## Downgrade
- Every `upgrade()` has a working `downgrade()` that reverses it.
- If a true reversal would lose data, say so in the result summary and in a code comment.

## Verification
**Online (preferred).** If a local database is reachable (the `DATABASE_URL` the repo uses is set, or the repo's docker-compose database is running):
1. `alembic upgrade head`
2. `alembic downgrade -1`
3. `alembic upgrade head`
4. `alembic heads` - there must be exactly one head.

**Offline (fallback).** If no database is reachable:
1. `alembic upgrade head --sql` - the SQL must render without errors. Check that it matches the contract DDL.
2. `alembic heads` - exactly one head.
3. Report in `checks`: "DB verification: offline only - no database reachable".

Never start, stop or reset a database container, and never point at a shared or non-local database.

## Report
In `summary`: tables and columns changed, whether existing data is affected, and lock or backfill notes.
In `memory_note`: revision ID, down revision, and any follow-up (for example, "contract step needed in a later release").
